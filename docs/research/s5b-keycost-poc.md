# Модель стоимости группы ключей: PoC, до любого нового прогона

Локальный gate, без Actions. Модуль `execution/s5b_execution/keycost.py`
к планировщику НЕ подключён — и это проверяется импортом, а не
обещанием. `UNDIVIDED_SHARE` по-прежнему `None`.

## Зачем: планировщик рассогласован сам с собой

После калибровки это видно детерминированно, без нового вычисления.

```
groups_needed()  выбирает g по Амдалу:   T_full * (s + (1 - s) / g)
units_for()      даёт группе вес:        T_full * len(keys) / 72
```

Второе теряет повторяемую долю `s` и считает все ключи равными, хотя
калибровка показала разницу в 2.69 раза. Проверено подстановкой
`UNDIVIDED_SHARE = 0.0383` в памяти процесса, для худшей руки 64000
(`r96.0:c1.25:R0:m1.0`, масштаб огибающей):

```
ключей   планировщик думает   профиль даёт
  15          2.03 ч              1.67 ч
  15          2.03 ч              1.74 ч
  15          2.03 ч              1.92 ч
  15          2.03 ч              2.75 ч   выше бюджета
  12          1.62 ч              3.15 ч   выше бюджета
```

Худшая группа: 2.03 ч по планировщику, 3.15 ч по измерению — недооценка
55%, и план прошёл бы проверку бюджета. Хуже того, хвостовую 12-ключевую
группу планировщик считает САМОЙ ЛЁГКОЙ, а она самая тяжёлая: все её ключи
из блока 60.0. Порядок групп у него перевёрнут.

**Поэтому выставить `UNDIVIDED_SHARE` сейчас нельзя.** Планировщик
перестанет падать и начнёт строить заведомо неверный план.

## Модель

```
T(G) = S + sum(cost(k) for k in G)          S повторяется в каждой группе
```

Стоимость ключа известна только по ПЕРВОЙ координате — только она
измерена. Внутри блока ключи считаются равными; это ДОПУЩЕНИЕ.

## Подгонка и проверка

Подгонка по C1 и четвертям g=4: пять неизвестных (S и четыре блока) на
пять наблюдений. Она ТОЧНАЯ, степеней свободы ноль, поэтому
воспроизведение C4, W4 и дисбаланса четвертей ничего не доказывает.

```
S = 95.0 с на группу
блок  1.0: 21.95 с/ключ    блок 15.0: 28.07 с/ключ
блок  5.0: 23.59 с/ключ    блок 60.0: 58.97 с/ключ
```

**Проверка — вариант g=2, в подгонку не входивший.** Допуск объявлен в
коде до сверки: 5% на группу, на C и на W. Обоснование: на порядок меньше
запаса до бюджета у решений, ради которых модель нужна (10–14%), и выше
правдоподобного шума однократного замера.

Оговорка о слепоте: невязки на половинах частично уже были видны через
оценки s_A и s_B в прошлом разборе. Проверка не слепая; допуск объявлен
от величины решения, а не подобран под невязку.

```
                     замер     модель    ошибка
половина 0           898.6     914.8     +1.81%
половина 1          1661.3    1661.9     +0.03%
C2                  2559.9    2576.7     +0.66%
W2                  1661.3    1661.9     +0.03%
дисбаланс половин    1.849     1.817
худшая ошибка 1.81% при допуске 5%  ->  PASS
```

**У проверки есть различающая сила.** Та же сверка для модели РАВНЫХ
ключей — нынешнего допущения планировщика — даёт +43.4% и −22.5%: KILL.
Проверка не штамп: она принимает профиль и отвергает то, что
планировщик делает сейчас.

## Что модель говорит о 64000

Условно: линейность по просмотру — допущение, а не замер.

```
                             масштаб раннера x16   масштаб огибающей
полный юнит                        11.03 ч              9.74 ч
смежная раскладка                  g = 11               g = 8
LPT по стоимости ключа             g = 6                g = 5
идеальная граница S + Σ/g          g = 6                g = 5
```

Прошлое «около 6» опиралось на идеальную границу. Настоящее разбиение на
целые ключи (LPT) её достигает — в масштабе раннера потому, что 18 ключей
блока делятся на 6 нацело.

## Находка: «сбалансированный» LPT выровнен по неизмеренной оси

Внутри блока ключи по модели равны, и LPT раскладывает их по кругу в
каноническом порядке. Период круга 6 = 3 горизонта × 2 значения
`maximise`, поэтому при g = 6 каждая группа получает ровно ОДНУ клетку:

```
LPT, g=6:   группа 0 — только horizon 300,   maximise False
            группа 5 — только horizon 86400, maximise True
```

По модели баланс идеален. По горизонту — наихудший из возможных. Если
стоимость зависит от горизонта (диапазон 300 -> 86400, в 288 раз),
«сбалансированное» разбиение окажется самым несбалансированным. Смежная
раскладка, для сравнения, горизонты перемешивает.

**Исправление бесплатно по модели.** Факториальное разбиение: ключ идёт в
группу `(2h + x + 2d + t) mod 6`. Каждая группа получает по 3 ключа из
каждого блока (стоимость по модели та же, 2.190 ч) и при этом по 4
каждого горизонта, по 4 каждого `days`, по 6 каждого `maximise`.
Аддитивный вклад неизмеренных координат делится между группами поровну.
Построено только для g = 6; для других g это правило не выводится и
отказывает.

Обратная сторона той же находки: LPT-группы — идеальный ЗОНД для
неизмеренных осей. Опасные для планирования, они изолируют каждую клетку
`(horizon, maximise)` и измерили бы её вклад напрямую.

## Что осталось эмпирическим

Этот gate снял то, что снимается без вычислений. Остаются два вопроса,
которые моделью не закрыть:

- **Межпрогонная устойчивость профиля.** Нас интересуют не секунды, а
  сохранение порядка `1.0 < 5.0 < 15.0 < 60.0`, отношений и полосы `s` на
  другом раннере.
- **Линейность по просмотру.** Все числа 64000 висят на ×16.

И третий, открытый этой проверкой: **равномерность внутри блока**.
Нынешняя калибровка её не видит вовсе: смежные четверти содержат все
горизонты поровну, так что вклад горизонта между группами не меняется.
