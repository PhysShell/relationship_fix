# 2D-0 — Решение об источнике приёма

Статус: **A и B отклонены, C — основной кандидат, не подтверждён.** Реализация
не начинается до закрытия шага 1 спайка (ToS) и шага 3 (живая авторизация).

Вход задачи — замороженный [`C_target`](c-target-spec.md): рутинный
person-period содержит **ноль действий человека**. Источник выбирается под это
требование, а не наоборот.

## Три варианта

### A. Watcher папки с экспортом Telegram Desktop — **REJECT как `C_target`**

```
Telegram Desktop
  → Export chat history      ← человек делает это КАЖДЫЙ период
  → наша папка / watch
  → автоматический приём
```

Мы убрали загрузку файла и оставили сам экспорт — крупнейший touchpoint
протокола, который `C_target` объявил `REMOVABLE`. Это не ноль рутинных
действий, а меньшее число экранов вокруг того же действия.

**Отклонён именно как `C_target`, а не вообще.** Остаётся как:

- reference/developer acquisition path — семантика уже квалифицирована, ledger
  закрыт, 25k-артефакт сертифицирован;
- возможный recovery path для участника, если основной источник недоступен.

Но называться `C_target` он не может: документ говорил бы «0 routine actions»,
а продукт каждую неделю просил бы открыть Telegram и выгрузить JSON. Это
расхождение не косметическое — оно на уровне причинного дизайна.

### B. Прямое чтение `tdata` — **REJECT**

Новый источник с реверс-инженерной семантикой, собственными зашифрованными
структурами и — главное — **без гарантии, что там вообще лежит полная история
чатов**: локальное хранилище десктопа предназначено для настроек и кэша, а не
для того, чтобы быть источником истины о переписке.

```
UX потенциально хорошо
семантика плохая
нужных данных гарантированно не даёт
```

Мы уже потратили неделю на forensic reading чужого экспортёра. Повторять это на
зашифрованном формате без контракта — не исследование, а развлечение.

### C. Telegram API / TDLib — **PRIMARY CANDIDATE**

```
РАЗОВО при зачислении:
    авторизация Telegram
    выбор целевого personal chat
    ──────── дальше рутинных действий нет ────────

каждый период (без участия человека):
    локальное приложение → TDLib → нужный интервал
    → source qualification → adapter → FROZEN extractor → только агрегаты
```

Это единственный из трёх вариантов, где рутинный person-period **пуст**.

## Что уже установлено по контракту

Ledger: `extractor/adapters/telegram_tdlib.py`. **9 свойств — 4 QUALIFIED ·
2 PARTIAL · 3 UNKNOWN**, открытых допущений **2**.

| находка | источник |
|---|---|
| TDLib под **Boost Software License 1.0** — пермиссивная, встраивается в продукт | `LICENSE_1_0.txt` + README §License, прочитаны |
| `messages.getHistory`: **«Results are ordered by date (descending)»** — порядок объявлен явно | core.telegram.org/method/messages.getHistory |
| запрос диапазона существует: `offset_date`, `min_id`, `max_id` | таблица параметров того же метода |
| `limit` ≤ 100, и **TDLib сам выбирает фактическое число** | core.telegram.org/tdlib/docs, `getChatHistory` |
| **продюсер артефакта — мы**; Telegram Desktop уходит из пути приёма целиком | следствие встраивания библиотеки |

**Три улучшения против экспортного пути, каждое закрывает конкретную боль.**

Порядок объявлен **по дате**, а не «typically ... descending object ID values» —
это принципиально сильнее того, что давал экспорт.

Диапазон **можно запросить**. У экспорта запрошенный диапазон не соблюдался семь
лет: #5854 (2019) · #27183 (2023) · #30412 и #31082 (2026). Окно всё равно
остаётся протокольным — запрос это удобство, а не источник истины о покрытии.

`provenance.producer_version` — худшая строка экспортного ledger'а — **исчезает
по конструкции**. Версия чужого GUI-клиента больше не нужна, потому что чужого
GUI-клиента в пути нет. Это и закрывает §4 `C_target`: не автоматизацией поля
ввода, а удалением вопроса.

## Что НЕ установлено — и почему это важнее

Шаги 2–6 спайка требуют живого Telegram-аккаунта и **не выполнены**. Документация
вендора — свидетельство о намерении, не измерение.

| открыто | что решает |
|---|---|
| **применимость условий не подтверждена** | ToS прочитаны — см. [tdlib-terms-applicability.md](tdlib-terms-applicability.md). Условия адресованы «Telegram-like messaging applications», а Content Licensing разрешает доступ закрытым перечислением Client/Bot/Mini App «solely to the extent strictly required to operate the relevant service». Текст читается **скорее против нас**, а не нейтрально. **Блокирует реализацию** |
| **AI/ML — прямой запрет** | §1.5 API Terms: данные из Telegram нельзя использовать для обучения, разработки или развёртывания AI/ML. Исключение требует согласия **всех** участников чата — для диады это оба партнёра. Введён архитектурный firewall |
| **разовость авторизации не проверена** | если она повторяется каждый период, `C_target` недостижим и весь смысл перехода исчезает |
| **два документа вендора описывают порядок по-разному** | MTProto: по дате. TDLib: «reverse chronological order (i.e., in order of decreasing message_id)». Совпадают только если `id` монотонен по времени — то самое, что мы отказались предполагать |
| `only_local` | офлайн-режим по локальной базе: новый механизм молчаливого усечения, класс тот же, что 10000-сообщений у экспорта |
| короткая страница | «число выбирает TDLib» — значит страница короче `limit` **не** признак конца истории. Пагинация обязана заканчиваться по курсору |

### Что при этом НЕ придётся переоткрывать

`TiePolicy.STRICT` снял допущение о порядке внутри секунды **конструкцией**.
Поэтому что бы ни оказалось в скобке у вендора, cross-actor-группы с равной
секундой помечаются неоднозначными, и **замороженное ядро не трогается ни при
каком ответе**. Работа, сделанная на прошлом источнике, окупилась ровно здесь.

## Порядок TDLIB-0

```
1  лицензия и deployment fit        ЧАСТИЧНО: лицензия ✔,
                                    ToS прочитаны, применимость ✗  ← блокирует
2  поднять локальный TDLib-клиент   не начато
3  авторизовать тестовый аккаунт    не начато — НУЖЕН ЖИВОЙ АККАУНТ
4  выбрать один personal_chat       не начато
5  забрать несколько страниц        не начато
6  посмотреть сырые поля            не начато (extractor не кормить)
7  достроить SourceSemantics ledger ЧАСТИЧНО: контрактная часть ✔
8  решить, удовлетворяет ли источник замороженные допущения ядра — после 2–6
```

Шаг 6 отдельно: **сырые поля смотрим, extractor не кормим.** Сначала семантика,
потом данные — правило, которое на прошлом источнике стоило четырёх исправленных
ошибок.
