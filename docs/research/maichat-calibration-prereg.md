# PHASE S3 — MaiChat как калибровочный корпус: вопросы ДО просмотра

Статус: **зарегистрировано до первого запуска** (2026-09-18). Ни одно число из
корпуса на момент написания не посчитано; прочитаны только README (схема,
методология, лицензия) и код адаптера.

## 0. Роль корпуса: калибровка, НЕ валидация

MaiChat уже использовался в этом проекте (external qualification экстрактора),
и сейчас мы сознательно смотрим на него, чтобы оценить правдоподобие
генератора. Значит он **calibration/stress corpus**, и называть его потом
independent validation set нельзя.

> **Запрет, действующий бессрочно.** Ни один будущий документ не «подтверждает»
> на MaiChat то, что с помощью MaiChat было подстроено. Переобучение люди
> изобрели и без нашей помощи.

Если после просмотра генератор правится, маркировка ровно одна:

```
НЕТ:  подкрутили параметры → снова MaiChat → похоже → VERIFIED
ДА:   MaiChat discrepancy observed → generator amended
      → MaiChat becomes calibration evidence
```

И **новый генератор получает новый golden trace digest**. Нынешний (87
сообщений, sha256 `24e0c1e3…`) после смысловой правки процесса обязан умереть
демонстративно. Это feature, а не неудобство: он существует ровно для того,
чтобы объявить, что все прежние числа относились к другому процессу.

## 1. Чего этот корпус структурно НЕ может — объявлено до просмотра

Три факта из README и адаптера, каждый из которых сужает вопрос:

### 1.1 Часы другие

MaiChat хранит **server-receive** метки с **миллисекундной** точностью
(README §1, §3; `TimestampSemantics.SERVER_RECEIVE`). Telegram отдаёт
**секундные** метки часов **отправляющего устройства**. Это разные и по
смыслу, и по разрешению величины.

Следствие: доля cross-actor ties в родном разрешении MaiChat к нашему вопросу
отношения не имеет и будет околонулевой по построению. Поэтому tie pressure
меряется **дважды**: в родном разрешении (описательно) и после **намеренного
огрубления до 1 секунды** (сравнимо с нашим генератором и с Telegram).

### 1.2 Сессия, а не person-period

Разговоры длятся **минуты** — harness не зря держит отдельную сетку
`SESSION_HORIZONS = 1/5/30 мин` рядом с продуктовой 6/12/24 ч. Наша единица —
person-period в 14 суток.

Следствие: величины масштаба окна (**сообщений на person-period, N на период,
доля N = 0 по H, censoring fraction**) сравнению НЕ подлежат. Сравнивать можно
темпы и форму внутрисессионной топологии.

### 1.3 Синхронная сессия незнакомцев по записи, а не живая переписка

README §5: участников **рекрутировали и разбивали на пары**, каждая проводила
**свободный разговор в реальном времени** через платформу. Обе стороны
присутствуют и внимательны.

Это самое важное ограничение, и именно для нашей метрики:

> `reentry_burden_H` живёт в ХВОСТАХ. Синхронная назначенная сессия хвосты
> подавляет конструктивно: долгого молчания там почти не бывает, потому что
> люди сели поговорить.

Следствие: **хвост латентности, доля неответа и суточный ритм по MaiChat не
калибруются вовсе.** Час суток в нём отражает время, на которое назначили
сессию, а не ритм жизни пары.

### 1.4 Что из этого следует для вопроса «правдоподобен ли генератор»

| параметр генератора | калибруется по MaiChat? |
|---|---|
| `within_burst_seconds`, `burst_continue_p` | да, с поправкой «синхронно = быстрее» |
| короткая часть `conditional_reply_speed` | да, как **нижняя** граница по времени |
| `timestamp_resolution_seconds` / tie pressure | да, **как верхняя граница** (см. §2.1) |
| `latency_log_mean`, `latency_log_sd` (хвост) | **нет** |
| `nonresponse_p` | **нет** |
| `night_suppression`, границы ночи | **нет** |
| `opportunity_rate_per_day` | **нет** (окно другого масштаба) |

Половину параметров генератора этот корпус не трогает. Это не повод его не
смотреть — это повод не притворяться, что посмотрели.

## 2. Четыре вопроса, зафиксированные заранее

### 2.1 Tie pressure

Считается раздельно, а не одним числом:

| величина | зачем |
|---|---|
| групп с одинаковой меткой времени | сколько вообще одновременности |
| из них cross-actor | только они ломают топологию |
| `ambiguous_opportunities / (ambiguous + eligible)` | цена, которую платит `STRICT` |
| та же доля **по каждому H** | цена зависит от горизонта |

Каждое — в родном разрешении и после огрубления до 1 с.

**Почему это верхняя граница.** Плотная синхронная сессия даёт больше шансов
на совпадение секунды, чем разреженная естественная переписка. Если даже здесь
доля сотые процента — `TiePolicy.STRICT` дёшев, и `BOUNDED` остаётся в папке
«умные вещи, которые нам пока не пришлось писать». Если проценты — мы узнали,
что synthetic timestamp model слишком аккуратен, и у strict exclusion есть
реальная цена.

Предсказание генератора, сделанное до просмотра: **0.048%**. Я буду рад, если
его разнесёт: несовпадение здесь информативнее совпадения.

### 2.2 Форма процесса

Сравнивается по квантилям (см. §3), раздельно по классам сравнимости:

| величина | класс |
|---|---|
| partner-run message count | сравнимо |
| `partner_run_span` | сравнимо |
| `conditional_reply_speed` | сравнимо в короткой части, хвост — нет |
| `partner_run_start_to_reentry` | сравнимо в короткой части, хвост — нет |
| сообщений на person-period | **НЕ сравнимо** (§1.2) |
| N (число возможностей) на период | **НЕ сравнимо**; сравнивается ТЕМП, §2.3 |
| доля N = 0 по H | **НЕ сравнимо** |
| nonresponse / censoring fraction | **НЕ сравнимо** (§1.3) |
| час суток | **НЕ сравнимо** (§1.3) — назначение сессии, не ритм |

Вопрос не «совпало ли», а:

> лежит ли синтетический процесс хотя бы в человеческом диапазоне, или мы
> моделируем очень дисциплинированных радиолюбителей с расписанием.

### 2.3 Распределение N — отдельным пунктом

Уже установлено: `B = Σ min(T, H)`, `R = B / N`, и `N` способен менять
интерпретацию сильнее, чем длительность. Генератор, который прекрасно
воспроизводит латентность, но производит втрое больше возможностей, даёт
совершенно другую power landscape.

Поскольку N на период несравним (§1.2), сравнивается:

* **темп возможностей** — возможностей на минуту активного разговора;
* **форма распределения межвозможностных промежутков** по квантилям.

### 2.4 Хвосты, а не медиана

Сетка квантилей для каждой сравнимой величины: **p50 / p75 / p90 / p95**.
Никакого фестиваля p-value по каждой колонке: n = 50 разговоров (≤ 100
person-periods), и p90/p95 будут широкими. Разброс сообщается, значимость — нет.

## 3. Правило решения, записанное до просмотра

Для каждой сравнимой величины: `r_q = synthetic_q / maichat_q` на сетке
квантилей, и скаляр

```
D = max по сетке | log2 r_q |
```

| D | исход |
|---|---|
| `D <= 1` (везде в пределах ×2) | **IN RANGE** |
| `1 < D <= 2` (в пределах ×4) | **MARGINAL** |
| `D > 2` | **OUT OF RANGE** |

Порог не выведен из природы, он **назначен до просмотра** — в этом весь смысл.
Обоснование: собственная межпарная гетерогенность генератора
(`latency_log_sd_between = 0.5`) уже растягивает медиану примерно в ×2.7 между
краями ±1 SD, так что ×2 на объединённом распределении — внутри уже
моделируемого человеческого разброса. ×4 меняет power landscape существенно,
поскольку дисперсия входит в квадрате.

Четвёртый исход обязателен и не является отказом от работы:
**NOT COMPARABLE** — структурное несоответствие из §1 запрещает сравнение.
Величина всё равно считается и печатается, но вердикта не получает.

## 4. Манифест запуска

Первый результат, который пойдёт в научную запись, обязан быть
воспроизводимым независимо от того, насколько удачный сегодня seed. Поэтому до
получения чисел фиксируется манифест:

```
generator digest        golden trace sha256
master seed             корень всех потоков
trial / replicate count
parameter grid          Population + DyadParameters
pairing policy          paired / unpaired
simulation code commit  git sha
corpus version + path   MaiChat v1.0, 50 файлов
```

Это же закрывает один из двух сознательно оставленных мутационных пробелов
(посев и спаривание внутри `coverage_probe`) — не прибиванием конкретного
вызова RNG, а требованием, чтобы таблица через месяц воспроизводилась.

## 5. FREEZE после S3

По результатам замораживаются три вещи, и только потом начинается S2:

1. **generator parameter envelope** — какие параметры и в каких пределах
   считаются откалиброванными, а какие остаются необоснованными;
2. **discrepancy notes** — что разошлось, на сколько, и что с этим сделано;
3. **run manifest** — §4.

## 6. Чего этот этап НЕ установит

* что генератор реалистичен — половина его параметров (§1.4) корпусом не
  трогается вовсе;
* что хвосты латентности правдоподобны — синхронная сессия их подавляет;
* что суточный ритм правдоподобен — в корпусе его нет;
* что `0.048%` перенесётся на Telegram — MaiChat даёт **верхнюю** границу, и
  граница не есть значение;
* что пайплайн верен — это S1, и он про другое.
