## Отказ слияния

```
s5b_stage1_cli.py: error: unrecognized arguments:  --look 4000
```

Ведущий пробел в `" --look"` — вся причина. Шаг `merge` был записан
ПЛОСКИМ скаляром YAML:

```yaml
run: python3 -B -m tools.s5b_stage1_cli merge \
       --look ${{ ... }} --out ../../out
```

В плоском скаляре YAML сворачивает перенос строки в пробел. `\` перестаёт
быть продолжением команды и становится экранированием пробела, то есть
оболочка получает аргумент `" --look"`. Три остальных `run:` в том же
файле записаны блочным `run: |`, где перенос сохраняется и `\` работает.

Ошибка была в единственном шаге, который до сегодня ни разу не исполнялся.
`plan` отрабатывал при каждой проверке, `run` — на дымовой пробе, `smoke` —
там же. `merge` не отрабатывал никогда.

### Находка 1: стоимость аффинна по ставке, а модель пропорциональна

`cost_of` считает стоимость пропорциональной эффективной ставке. Внутри
ОДНОГО шарда истинная зависимость аффинна, `a + b * rate`, и подгоняется
с `R2 = 0.983..0.996`.

Механизм очевиден задним числом: у каждого периода есть работа, не
зависящая от числа событий — сдвинуть часы, обновить окно, тронуть
аккумулятор. По событиям масштабируется только их собственный цикл.
Фиксированное слагаемое даёт 31–43% стоимости при ставке 1 и 0.4% при
ставке 120. Отсюда разброс `sec/rate` в 2.3 раза, который легко принять
за шум.

### Находка 2: раннеры отличаются почти вдвое

Наклоны `b` по шести шардам: `9.374, 16.538, 9.264, 18.132, 13.153,
18.187`. Нормированные на минимум (в порядке шардов 0..5): `1.012, 1.785, 1.000,
1.957, 1.420, 1.963` — то есть не два класса, а по меньшей мере четыре уровня, и
крайние отличаются в `1.96` раза.

Именно поэтому общая подгонка по всем 156 юнитам даёт всего `R2 = 0.881`
против `0.99` внутри шарда: пул смешивает раннеры разной скорости.

### Находка 3: модель завышает ИТОГ и занижает ХУДШИЙ ШАРД

худший   модель  3.573 ч      факт  4.188 ч      модель НИЖЕ на 17.2%

Это не противоречие, а прямое следствие допущения об одинаковых раннерах.
Итог усредняет случайную смесь скоростей и потому выходит примерно верным.
Худший шард определяется САМЫМ МЕДЛЕННЫМ вытянутым раннером, и его модель
не описывает вовсе. В потолок упирается именно худший шард.

**`SHARD_BUDGET_HOURS = 4.0` пробит фактом на первой же производственной
ступени: `4.188 ч`.** Платформенный потолок `5.83 ч` (таймаут 350 минут)
устоял, запас составил `1.39 ч`.

### Снимается прежний тезис о балансировке

В ходе прогона было сказано, что поюнитный промах модели делает
балансировку самообманом. **На этих данных это не подтвердилось.** Шарды
0 и 2 попали на раннеры одного класса и сошлись по факту на `0.4%`
(`7656.5` против `7628.7`) при предсказанных весах, совпадающих до
`0.01%`. При ~26 юнитах на шард поюнитная ошибка усредняется, и LPT
работает.

Тезис остаётся открытым только для мелкой нарезки: на 64000 план даёт
1–4 юнита на шард, и усреднять там нечего. Но это предположение, а не
измерение.

## Что этот прогон НЕ проверил

**Ось ключей не включалась ни разу.** На ступени 4000 `groups_needed`
равен единице у всех 156 рук; на 16000 — тоже. Деление по ключам
активируется только на 64000 (1–3 группы). Переработанный слой шардинга
по ключам производственно не испытан.

**`GENERATION_SHARE = 0.05` не участвовал.** При одной группе ключей
множитель доли равен единице тождественно.

**Линейность по `look` не проверена.** Все юниты посчитаны на одной
ступени. Пересчёт аффинных коэффициентов на 16000 и 64000 — экстраполяция.

**`s5b_shard.merge()` не вызывается CLI вовсе.** Режим `merge` проверяет
только полноту набора `task_id` и печатает дайджест. Сборка концов по руке
с её семью путями отказа покрыта юнит-тестами и в производственный путь не
подключена. На 4000 и 16000 это безвредно: у каждой руки ровно один юнит,
собирать нечего. На 64000 рука дробится на 2–3 юнита, и сборка
понадобится. **Это дефект, а не особенность.**

## Наука первой ступени

Концов всего `33696` = 156 рук x 72 ключа x 3 значения `delta`.

```
delta = 0.01*H (36 с):  достигнуто точности      0 / 11232 =  0.0%
delta = 0.03*H (108 с): достигнуто точности   1291 / 11232 = 11.5%
delta = 0.10*H (360 с): достигнуто точности   9336 / 11232 = 83.1%
```

На уровне ЯЧЕЕК, где по ревизии 4 требуется, чтобы точности достигли все
четыре конца сразу:

```
ячеек 15552, оценимо 4617 = 29.7%
  delta = 0.01*H :    0 / 5184 =  0.0%
  delta = 0.03*H :  433 / 5184 =  8.4%
  delta = 0.10*H : 4184 / 5184 = 80.7%
```

Лестница ведёт себя как лестница: самая тесная цель не останавливается
нигде, самая мягкая — в четырёх случаях из пяти. Ни одна ячейка не
сертифицировалась преждевременно. `tau = inf` на 4000 для 70.3% ячеек —
это `MC_PRECISION_INSUFFICIENT`, то есть отказ, а не результат.

### Содержательное наблюдение: R4 теряет точность монотонно по magnitude

```
R1 m0.5 33.5%   R2 m0.5 33.3%   R3 m0.5 32.7%   R4 m0.5 28.5%
R1 m1.0 33.5%   R2 m1.0 32.9%   R3 m1.0 32.4%   R4 m1.0 20.8%
R1 m2.0 32.9%   R2 m2.0 31.7%   R3 m2.0 31.7%   R4 m2.0 12.3%
```

R1–R3 держатся ровно на 32–33% и по magnitude почти не меняются. R4 падает
с 28.5% до 12.3%.

Это согласуется с замороженной семантикой R4: эффект там — монета на пару
(`2*LATENCY_SHIFT` либо `0`), то есть гетерогенный, тогда как у остальных
режимов он однородный. Гетерогенность раздувает дисперсию, дисперсия
расширяет множество приёма, радиус растёт, и критерий точности не
выполняется. `magnitude` масштабирует сдвиг, поэтому эффект усиливается.

Механизм согласован с наблюдением, но ПРОВЕРЕН на нём не был:
это наблюдение одной ступени, а не проверенная гипотеза. Прямая проверка —
сравнить радиусы R4 и R1 при равном среднем эффекте — не делалась.

Операционное следствие реально в любом случае: утилита лестницы
`P(tau < inf)` зависит от режима, и R4 потребует больше просмотров.
