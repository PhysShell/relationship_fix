# Ступень 16000: результат и локальный аудит переноса

Прогон `35904117457`, заявка `10f2d99`, `SCIENCE_SHA = 7a62a39`,
`EXECUTION_SHA = a9cbc94`, пин слоя `78e887fc`.

## Аудит: перенос доказан ПО ИДЕНТИЧНОСТЯМ, а не по счётчику

`ignored_because_already_settled = 10627` совпало с `carried` из плана, но
счётчик не различает «сохранили те же 10 627» и «потеряли один, а другому
ошибочно присвоили 4000». Равенство мощностей не есть равенство множеств.

**Метод.** Левая часть выведена из 156 part-файлов ступени 4000 НАПРЯМУЮ,
без `Ledger`: конец закрыт на 4000 тогда и только тогда, когда статус в
его payload'е равен `MC_PRECISION_ACHIEVED`. Иначе сверка спрашивала бы у
программы, права ли программа. Правая часть — `checkpoint.json`,
написанный производственным прогоном. Идентичность конца =
`(рука, ключ, доля)`; просмотр в неё не входит.

```
ЛЕВАЯ   закрылось на 4000:      10 627    дублей идентичности 0
ПРАВАЯ  tau=4000 в чекпойнте:   10 627    дублей идентичности 0
распределение tau в чекпойнте:  {4000: 10627, 16000: 6659}

missing    (4000 \ carried)               0
unexpected (carried \ 4000)               0
collisions                                0 / 0
расхождений в содержимом 10 627 концов    0
   сверялись key, fraction, point, low, high, radius, status, look
перенесённых с look != 4000 в payload     0
перенесённых со статусом != ACHIEVED      0

IDENTITY EQUALITY: PASS
```

Разложение `17 286 = 10 627 @ tau=4000 + 6 659 @ tau=16000` прочитано из
чекпойнта, а не получено вычитанием.

## Аудит: переиспользование между разными EXECUTION_SHA

`resume.completed` и `resume.origin` пересчитаны на настоящих частях
отменённого прогона `35839807992` и сверены с записью артефакта:

```
reused             15                  = 15
parts_digest       c48ed56c4f610917    = c48ed56c4f610917
task_ids_digest    4119c4144223a5a1    = 4119c4144223a5a1
from_science_sha   7a62a39...          = 7a62a39...
from_execution_sha a68f310d...         = a68f310d...
from_request_sha   3a4054c...          = 3a4054c...
```

Два контроля, а не одно утверждение:

```
EXECUTION_SHA частей (a68f310d) != EXECUTION_SHA прогона (a9cbc94)
    и части ПРИНЯТЫ: допустимость от слоя исполнения не зависит
подмена SCIENCE_SHA в копии манифеста -> отказ «это разные вычисления»
научные координаты каждой части = манифест цепочки
task_id и отпечаток содержимого выводятся из состава самой части
```

Это первый случай, когда переиспользование через смену `EXECUTION_SHA`
подтверждено на производственных артефактах, а не только тестом.

## Аудит: чекпойнта достаточно для воспроизведения выхода

```
Ledger.from_checkpoint  отпечаток сверён внутри -> 7ef59277bf6acc6b
ячеек     15 552 = 15 552        оценимых 7 778 = 7 778
ячейки    побайтово те же
output_digest  9a988f441bec23e1 = 9a988f441bec23e1
```

Именно это свойство понадобится на следующей ступени: сырые части 16000
не содержат концов, остановившихся на 4000.

## Провенанс проверки

Каждый скачанный артефакт сверен по sha256 с тем, что объявили логи его
прогона: `s5b-reduced-16000` (`5e6456af…`), шесть шардов и манифест
ступени 4000, манифест и четыре шарда отменённого прогона. Двенадцать
отпечатков из двенадцати. Проверка read-only, репозиторий не менялся,
Actions не запускались.

## Диагностика: полностью закрывшихся рук НЕТ

```
полностью закрывшихся рук после 16000:  0 из 156
закрыто концов на руку:  мин 48, медиана 113, макс 145  из 216

R0  12 рук   118.1 из 216
R1  36 рук   122.8
R2  36 рук   116.1
R3  36 рук   119.2
R4  36 рук    82.7
```

Практически это важнее среднего отношения времён: **ранняя остановка руки
пока вообще не начинает экономить вычисления.** Даже лучшая рука закрыла
145 концов из 216, худшая 48. Следующая ступень нужна не ради пары
упёртых рук, а потому что не закрылась ни одна.

НАБЛЮДЕНИЕ, А НЕ ОБЪЯСНЕНИЕ: у R4 закрытых концов заметно меньше (82.7
против 116–123 у R0–R3). Связь с его гетерогенной семантикой (половина
пар получает удвоенный сдвиг, половина ноль) правдоподобна и остаётся
гипотезой: на этом она не проверялась.

## Диагностика: масштабирование времени НЕ восстановлено

Пар «одна рука на обеих ступенях» всего 15 — только те, что успел
посчитать отменённый прогон. Отношение 16000/4000: медиана 2.84, от 2.18
до 7.49; peak RSS 100–113 МБ -> 218–363 МБ.

Законом масштабирования это не является: обе стороны сняты на разных
раннерах, а измеренный разброс раннеров на 4000 составлял 1.96×, что
сопоставимо с разбросом самих отношений. На этих же 15 наблюдениях
внутрилуковые аффинные подгонки были совместимы ровно с 4×.

Полные 141 часть ступени 16000 лежат в 54 отдельных артефактах; их
загрузка ради 156 пар СОЗНАТЕЛЬНО НЕ ДЕЛАЛАСЬ. Она станет оправданной
только как вход планирования следующей ступени: makespan, runner-hours,
RAM, размер шарда, риск упереться в потолок задания.

## Ступень 64000 блокирована слоем исполнения, а не этим результатом

Проверено запуском на настоящем реестре после 16000:

```
units_for(64000, ledger) -> SplitEconomyUnmeasured:
  ставка 96 на ступени 64000: полный юнит 7.81 ч против бюджета 2.5 ч,
  а экономия деления ключей НЕ ИЗМЕРЕНА (UNDIVIDED_SHARE is None)
```

7.81 ч — это выше не только цели 2.5 ч, но и платформенного потолка
5.83 ч: полный юнит тяжёлой руки на 64000 был бы убит раннером. Значит
деление ключей на этой ступени ОБЯЗАТЕЛЬНО, а его экономия не измерена
ни разу: и на 4000, и на 16000 у всех рук `groups_needed = 1`, то есть
ось деления не включалась никогда.

Ступень 64000 поэтому не планируется. Результаты этого аудита её не
блокируют; блокирует неизмеренная экономия деления — и придуманного
коэффициента здесь не будет.
