# Дымовая проба этапа 1: форма квалифицирована, модель пересчитана

**Прогон:** `35769710129`, задание `106888045069`, `ubuntu-latest`,
2026-09-22. Артефакт `s5b-smoke`, `2526` байт, SHA256
`140c9c039f9e4fd699807f745d9743d9737b36d8a1db1c43f4dda99896aaf552`.

## Что проверялось

Самый дорогой юнит сетки целиком, а не уменьшенная копия: рука
`r96.0:c1.25:R0:m1.0` (эффективная ставка `120` в сутки), ступень `64000`,
одна из двух групп ключей.

Причина ровно одна: все оценки длительности сняты на машине разработчика
(`4 x Intel Xeon @ 2.10GHz`, `15 ГБ`, Python 3.11.15). Сравнивать их с
шестичасовым потолком GitHub — значит выдавать бенчмарк одной машины за
время исполнения другой. Уменьшенный юнит с экстраполяцией был бы той же
ошибкой, просто аккуратнее замаскированной.

## Результат

```
seconds       16035.7   = 4.454 ч
predicted                 3.610 ч
коэффициент               1.2343

peak_rss_mb     442.8   против 16 ГБ раннера
digest       b3d80674ae23c419
```

**Форма квалифицирована.** `4.454 ч` против платформенного потолка
`6.0 ч`: запас `1.55 ч`, задание завершилось успешно, артефакт выгружен.
Память не является ограничением вовсе — `443 МБ` из 16 ГБ.

**Бюджет шарда `4.0 ч` пробит фактом**, и модель стоимости оказалась
оптимистичной на `23.4%`.

## Модель пересчитана из замера, а не домножена

```
X = 16035.7 / (64000 * (120/6) * (0.05 + 0.95*0.5)) = 0.0238626 с/период
```

Прежнее `0.0193333` сохранено как `SECONDS_PER_PERIOD_BEFORE_SMOKE`:
запись того, на чём считался прежний план.

Последствия для сетки:

```
                     до пробы        после пробы
худшая рука, 1 группа   6.87 ч          8.48 ч
групп на неё                2               3
шарды по ступеням     5 / 18 / 79     6 / 22 / 95
худший шард             4.00 ч          3.99 ч
всего                  374.1 ч         465.7 ч
wall-clock при 20        18.7 ч          23.3 ч
```

Все три ступени по-прежнему укладываются в потолок матрицы `256`.

## Чего это НЕ значит

`0.0238626` — **одна точка**: один юнит, один раннер, один момент.
Производительность публичных раннеров плавает, и считать это число точным
было бы прежней ошибкой в новой обёртке. Запас держит не точность
калибровки, а `SHARD_BUDGET_HOURS = 4.0` при потолке `6.0`: полтора часа
сверху на то, что раннер окажется медленнее ещё в полтора раза.

## Третья ошибка подряд в одну сторону

Модель стоимости ошибалась трижды, и каждый раз оптимистично:

```
ставка сетки вместо эффективной     ~25%        поймано расчётом
формула вместо проверки раскладки   4.12 / 4.0  поймано расчётом
время на чужом железе               1.2343      поймано ТОЛЬКО прогоном
```

Первые две находки выводятся, третья — нет. Она и была причиной требовать
пробу на настоящем раннере, а не считать, что «должно хватить».
