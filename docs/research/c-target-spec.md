# `C_target` — минимальный общий пакет (шаги 2A–2C)

Статус: **заморожен на бумаге.** Реализация начинается после этого документа, а
не до него. Иначе очень легко автоматизировать текущую церемонию вместо того,
чтобы её выкинуть, и потом гордо показать улучшение latency.

Контекст: `C` — общий пакет обеих рук ([memo §1](control-arm-decision-memo.md)).
Его облегчение меняет причинный контраст, поэтому подпись под H1/estimand ставится
**после** заморозки `C_target`, а не до.

## 2A. Инвентарь текущего `C`

Из [instrumentation-qualification.md §5](instrumentation-qualification.md):
четыре touchpoint'а из четырёх — осознанные действия человека.

## 2B. Классификация

| touchpoint | нужен для validity/safety | может быть автоматическим | видит/делает человек | решение |
|---|---|---|---|---|
| onboarding и согласие | **да** (этика) | частично | да | **REQUIRED**, минимизировать, разово |
| ручной export → передача файла | **нет как ручное действие** | **да** | сейчас да | **REMOVABLE** |
| `producer_version` / платформа | **да** | вероятно да, см. §4 | сейчас да, каждый период | **AUTOMATABLE** |
| остальной provenance (hash, kind, chat type, adapter, время приёма, вердикт) | да | **да, полностью** | не обязан | **AUTOMATABLE**, машинно |
| уведомление об отказе | да, когда действие возможно | нет полностью | да | **EXCEPTION-ONLY** |
| повтор действия после отказа | **иногда** | зависит от причины | да | **EXCEPTION-ONLY**, не универсально |
| осведомлённость о наблюдении | неизбежна и этически необходима | нет | да | **REQUIRED**, минимизировать, **не маскировать** |
| endline на 14-й день | да | нет | да | **REQUIRED**, разово |

Строка про осведомлённость помечена «не маскировать» намеренно. Уменьшать её
количеством экранов — можно и нужно; уменьшать её тем, что человек хуже понимает,
что его измеряют, — нельзя. Это не оптимизация burden, это подрыв согласия.

## 2C. `C_target`

```
routine acquisition (каждый период):
    0 ручных экспортов
    0 рутинных вопросов о провенансе
    0 рутинных экранов подтверждения
    → человек не делает НИЧЕГО

exception path:
    наружу всплывают ТОЛЬКО исправимые отказы

разово:
    onboarding + согласие
    endline на 14-й день
```

Нормальный путь стремится к **нулю повторяющихся пользовательских действий**.
Человек видит только исключительный путь.

### Replacement, не addition

```
ПЛОХО:  старый ручной экспорт
      + новый локальный приёмник
      + fallback-загрузка
      + экран верификации
      + «подтвердите определённый чат»
      = минимизация C добавила три экрана
```

```
БЫЛО:   Telegram → Export → выбрать JSON → загрузить → сообщить версию → retry
СТАЛО:  local acquisition → qualification → aggregate
```

Каждый новый экран в этом проходе обязан **удалять** существующий, иначе он не
проходит.

## 3. Provenance: богатый машинный, бедный человеческий

Принцип: **provenance должен быть богатым; пользовательский provenance workflow —
бедным.** Это две разные вещи, и их постоянно путают.

Машина получает сама, человек не вводит ничего:

```
acquisition method · source kind · artifact hash · chat type
schema/features observed · acquisition timestamp · adapter version
qualification verdict
```

## 4. `producer_version` — открытый архитектурный вопрос, а не поле ввода

Telegram Desktop **не записывает свою версию** в экспорт (`provenance.producer_version`
= UNAVAILABLE, установлено по исходнику писателя). Отсюда НЕ следует, что её надо
спрашивать у человека каждую неделю.

Порядок вопросов:

**РЕШЕНО ИНАЧЕ (2D-0).** Вопрос снят не автоматизацией, а удалением: при переходе
на Telegram API/TDLib продюсером артефакта становимся мы, и чужой GUI-клиент из
пути приёма исчезает целиком. Версия Telegram Desktop больше не нужна никому.

Если основной источник не подтвердится и придётся вернуться к watcher'у,
действует прежний порядок: прочитать версию с машины автоматически; если нельзя —
capture once at enrollment, persist, спрашивать только при обнаруженном изменении
окружения, а не по расписанию.

Запрещено: «Введите версию Telegram Desktop: ______» каждый период.

## 5. Отказы: reason-specific, а не универсальный retry

Опасная модель, действующая сейчас по умолчанию: любой `REFUSED` → «попробуйте
ещё раз» → повторное действие человека. Для доброй половины причин повтор того же
действия бессмыслен: если источник не предоставляет нужное свойство, повторный
экспорт магически его не добавит.

Контракт: каждая причина отказа несёт **класс восстановления**.

```
RECOVER_AUTOMATICALLY   слой приёма чинит сам, человек не уведомляется
USER_ACTION_REQUIRED    есть осмысленное действие — и только тут спрашиваем
TERMINAL_FOR_THIS_ARTIFACT   объяснить один раз; retry того же файла не предлагать
```

Разложение по кодам, которые тракт **реально** производит сегодня:

| код | класс | почему |
|---|---|---|
| `missing_producer_provenance` | **RECOVER_AUTOMATICALLY** | §4: слой обязан попытаться сам; к человеку — только при провале |
| `consent_not_recorded` | **USER_ACTION_REQUIRED** | этика, обойти нельзя |
| `invalid_json` · `not_an_export` · `malformed_entry` · `unusable_identity_or_time` | **USER_ACTION_REQUIRED** | артефакт битый: нужен новый экспорт, действие осмысленно |
| `no_chat_type` · `no_messages_array` | **USER_ACTION_REQUIRED** | то же: файл не тот |
| `not_the_target_chat_type` · `not_a_dyad` | **TERMINAL** | файл исправен и не наш. Повтор ничего не изменит; объяснить один раз |
| `no_actor` · `no_usable_messages` | **TERMINAL** | источник не даёт нужного свойства; повторный экспорт не добавит |
| `participant_absent_from_export` | **USER_ACTION_REQUIRED** | вероятно выбран не тот чат — действие есть |
| `window_outside_export` | **RECOVER_AUTOMATICALLY** | окно протокольное; расхождение чинится на нашей стороне, а не человеком |
| `payload_outside_allowlist` | **TERMINAL**, и это **наш** баг | человеку не показывается вообще; это инцидент разработки |

Эту таблицу надо построить **до** того, как станет известна частота отказов.
Частота нужна для оценки UX-цены, семантика — нет. Если окажется 0,1% —
прекрасно. Если 20% — исключительный путь стал фичей, пришедшей убить
эксперимент, и знать это лучше по конструкции, а не по факту.

## 6. Burden budget — чтобы «мы автоматизировали экспорт» не принималось на веру

Не научный исход и не дашборд смерти. Пять чисел на person-period, измеряемые
одинаково для `C_old` и `C_target`:

```
user_actions              действий человека
user_prompts              обращений к человеку
manual_minutes            минут ручной работы
refusal_retries           повторов после отказа
measurement_screens       экранов, связанных с измерением
```

Приёмочная цель `C_target` для рутинного пути: **первые три — ноль**.
`refusal_retries` — только по `USER_ACTION_REQUIRED`. `measurement_screens` —
ноль в рутине, ненулевой в исключении.
