# Слой исполнения: последовательная процедура наконец исполняется

## Что было найдено

Замороженный `run_unit` делает ОДНУ оценку на ОДНОМ `M`:

```python
store = E.accumulate(unit.arm, 0, unit.look, wanted=unit.keys, **arm)
return E.endpoints_from(store, look=unit.look, z=z)
```

`endpoints_from` считает множество приёма один раз и ставит
`look = unit.look` тем концам, что уложились в порог. Функция
`s5b_precision.run_nested`, которая и реализует `τ = min{M : r_M <= порог}`,
производственным путём НЕ ВЫЗЫВАЕТСЯ вовсе — её зовёт только
квалификационная оснастка.

Значит на 16000 конец, остановившийся на 4000, переоценивается заново и
возвращает `A_16000` с `look: 16000`. Это не риск, а поведение по
умолчанию.

Хуже: надеяться, что «позже не хуже», нельзя. В геометрии Филлера
множество приёма бывает несвязным и неограниченным, радиус по `M` убывать
не обязан. Конец, точный на 4000, на 16000 может точность ПОТЕРЯТЬ. Ранний
`τ` из позднего просмотра не восстанавливается в принципе.

При этом семантика в замороженной науке ОБЪЯВЛЕНА:
`s5b_escalation.EACH_ENDPOINT_AT_ITS_OWN_TAU = True`, с прямым
предупреждением про подмену `A_16000(T)` на `A_64000(T)`. Не хватало
только проводки.

## Что реализовано

`execution/s5b_execution/`, стандартная библиотека:

- `identity.py` — личность конца `(рука, ключ, доля δ)`. `look` в личность
  НЕ входит: в этом весь смысл.
- `ledger.py` — реестр. Первый ACHIEVED фиксируется навсегда вместе со
  своим payload; последующие копии игнорируются и СЧИТАЮТСЯ; ступени
  впитываются строго по возрастанию (иначе `τ` перестаёт быть минимумом).
- `cost.py` — верхняя огибающая по шести НАБЛЮДЁННЫМ раннерам.
- `scheduler.py` — какие юниты дальше, сколько заданий.
- `reduction.py` — зовёт замороженные `S.merge`, `E.cell_is_evaluable`,
  `E.cell_contrast`.
- `provenance.py` — пять полей, ни одно не выводится из остальных.
- `cli.py` — `plan` / `run` / `reduce`.

## Три вещи, которые я поправил у себя по ходу

**Написал `merge_arm` и не подключил.** Ровно тот дефект, который
критиковал. Теперь `reduce` зовёт замороженное слияние на КАЖДОЙ ступени,
а не только на 64000: путь, впервые исполняемый в бою, — это тот самый,
что сегодня уронил прогон.

**Чуть не подставил экономию деления ключей.** `full / groups` означало бы
предположить ту самую экономию, которая не измерена. Теперь
`UNDIVIDED_SHARE = None` и ОТКАЗ, а не правдоподобная константа.

**Раскладка выводилась дважды.** Если `plan` и `run` независимо выводят
список юнитов, они могут разойтись — тот же класс, что уронил прогон.
Теперь раскладка пишется в манифест, а `run` её читает и сверяет
`task_id` с составом юнита.

## Три инварианта, закрытые перед заявкой на 16000

### 1. Заявка действительно только сигнал

Закрепить `EXECUTION_SHA` было НЕДОСТАТОЧНО. Сам YAML воркфлоу GitHub
берёт из triggering ref, а не из пина. Значит между пин-коммитом и
заявкой можно было переписать оркестрацию целиком, и все три SHA
напечатались бы честно при подменённом воркфлоу. Тройка врала бы ровно на
полшага.

`EXECUTION_PIN_COMMIT` + fail-closed diff `пин..заявка`: допустимый путь
ровно один — файл заявки. Проверка разделена: `changed_paths` дёргает
git, `assert_request_is_only_a_signal` — чистая функция над списком, и
тестируется именно она.

Заявке нужна история, иначе diff не построить, поэтому checkout заявки
идёт с `fetch-depth: 0`. Обрезанная история сделала бы гейт немым — на
это есть отдельная диверсия.

### 2. Отпечаток входа, а не номер прогона

`prior_run` якорем не является: `task_id` кодирует научные координаты, а
не байты реализации, поэтому совместимый чужой прогон даст ровно те же
имена файлов. Заявка несёт `prior_digest`, и редуктор обязан
воспроизвести его из скачанных частей.

`9e2f5b314e598bb7` получен ДВУМЯ независимыми путями: печатью старого CLI
при локальном слиянии и новым `reduce` по тем же 156 артефактам. Это не
самозаверение.

Каждый `reduced.json` несёт цепочку дальше: science_sha, execution_sha,
request_sha, look, prior_run, prior_digest, input_digest, output_digest.

### 3. Граница импортов доказана, а не объявлена

Execution-checkout — ПОЛНЫЙ репозиторий, и в нём лежит свой
`research/python`. Сегодня коллизии нет лишь потому, что в `PYTHONPATH`
попадает `exec/execution`, а не `exec`. Это свойство одной строки.

`assert_science_comes_from` проверяет `__file__` каждого научного модуля
против science-checkout и возвращает карту «модуль -> файл», которая идёт
в provenance. Граница становится и проверенной, и записанной.

## plan — это и есть preflight

Отдельной дымовой пробы новой обвязки НЕ делается. Порядок в `plan`:

    diff пин..заявка -> граница импортов -> скачивание чужого прогона
    -> сверка отпечатка -> сведение прошлой ступени -> манифест
    -> сверка task_id каждой строки -> бюджет -> выгрузка

Всё, что может обрушиться дёшево, обрушивается ДО появления матрицы.
`compute` ничего не выводит заново: читает манифест и исполняет.

## Измеренный предел параллелизма, которого нет в модели стоимости

Прогон 35839807992 (ступень 16000, 41 задание) в 09:16Z: РОВНО 20 заданий
исполняются, 21 в очереди. Предел параллелизма этого аккаунта на публичном
репозитории со стандартными раннерами — **20 одновременных заданий**.

Стоимостная модель оптимизирует ВРЕМЯ ОДНОГО ЗАДАНИЯ против потолка. Но
время прогона определяется не им, а

    wall_clock ~ ceil(заданий / 20) * время_задания

и эти две величины оптимизируются в РАЗНЫЕ стороны. Снижение бюджета
дробит работу мельче, каждое задание становится безопаснее, а число волн
растёт:

```
    41 задание по 2.50 ч  ->  3 волны  ->  ~7.5 ч     <- текущий прогон
    40 заданий по 2.50 ч  ->  2 волны  ->  ~5.0 ч
    38 заданий по 2.75 ч  ->  2 волны  ->  ~5.5 ч
    26 заданий по 4.00 ч  ->  2 волны  ->  ~8.0 ч
```

41 — худшее возможное число сразу за 40: одно задание уезжает третьей
волной в одиночку, пока девятнадцать слотов простаивают. Бюджет 2.5 ч был
выбран как «существенно ниже потолка», и это верно по отношению к таймауту
задания — но случайно попал в точку, где добавление одного задания стоит
двух с половиной часов календарного времени.

**Правило, которого планировщик пока НЕ реализует:** минимизировать
`ceil(n / concurrency) * budget`, а не только укладывать задание в бюджет.
Иногда это означает бюджет БОЛЬШЕ, а не меньше.

### Почему текущий прогон не прерван

Наука от раскладки не зависит, прогон корректен и закончится. Прерывание
стоило бы выброшенных ~8 CPU-ч уже посчитанного, нового цикла
«правка -> пин -> заявка» и вмешательства в идущий научный конвейер ради
примерно двух часов календаря. Находка записана и применяется к следующей
ступени, а не к этой.

### Для 64000 это уже не косметика

```
     95 заданий  ->  5 волн  ->  ~12 ч
    160 заданий  ->  8 волн  ->  ~20 ч
```

На 64000 впервые включается расщепление ключей, число заданий растёт
кратно, и цена промаха мимо кратного двадцати измеряется не часами, а
сменами. Планировать ступень, не учитывая предел параллелизма, значит
повторить сегодняшнюю ошибку с множителем.
