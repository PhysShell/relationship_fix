# Многопрогонная ступень: локальный гейт механики — PASS

Решение: GO на multi-run packaging 64000, local-only. До production
workflow — ровно один дешёвый локальный гейт на синтетике; не проходит
чисто — KILL многопрогонной стратегии; никаких Actions для проверки
механики.

Код — `execution/s5b_execution/multirun.py` и режимы CLI `plan --multirun`,
`select`, `progress`; гейт — `research/python/tools/s5b_multirun_gate.py`,
свидетельство — `s5b-multirun-gate.json`.

## Механика

```
plan --multirun      ОДИН полный манифест: юниты, task_id и состав заданий
                     от партий не зависят; упаковка — наименьшее число
                     заданий в бюджете 2.5 ч (тот же поиск, что дал 495)
партии               LPT второго уровня по весам заданий, <= 165 в партии,
                     выводятся из манифеста заново в каждом прогоне
select --run R       <= 165 невыполненных заданий в порядке партий:
                     оставшееся от прошлых партий идёт первым; исполняются
                     только невыполненные юниты задания
продолжение          планирует ступень заново и обязано получить ТОТ ЖЕ
                     манифест; в каталог ложится манифест первого прогона
                     байт в байт
progress             итог прогона, не наука: PARTIAL — код 0, упавшее
                     выбранное — код 1, COMPLETE — код 0, STOP — код 1
reduce               прежний, только при пустом остатке; незаконченную
                     ступень он и сам отвергает
прогоны              3 номинальных + 1 восстановительный; пятого нет
```

## Гейт — один запуск, PASS

Синтетика: ступень 4000 всей сетки, 156 юнитов, `plan --multirun` дал
11 заданий (поиск упаковки тот же, что дал 495 на 64000); потолок партии
4, партии 4 / 4 / 3. Счёт — настоящий `cli run` с подменённым
`S.run_unit` (концы детерминированы научными координатами, смесь
достигнутых и нет); остальное — настоящие `plan`, `select`, `progress`,
`reduce`. Эталон — один прогон всех 11 заданий того же манифеста.
Проверки записаны в докстринге гейта до запуска. 20 с, Python 3.11.15.

## Что гейт не покрывал — и чем покрыто

- **Ветку сведения от чекпойнта.** Синтетика 4000 не имеет прошлой
  ступени, а 64000 сводится от чекпойнта 16000. Та же механика на 16000
  от синтетического чекпойнта 4000 — три прогона против одного, наука
  побайтово та же — регрессионный тест `TheCheckpointBranchChainTests`,
  добавлен ПОСЛЕ гейта.
- **Байты манифеста при другой заявке.** В гейте у всех прогонов одно
  окружение, поэтому копия и свежий план совпали бы и так. Что
  продолжение под другим `REQUEST_SHA` несёт байты первого прогона —
  тест `TheContinuationCarriesTheFirstManifestTests`.
- **Воспроизводимость вердикта.** Гейт исполнен на рабочем дереве поверх
  `d382a76`; sha256 на момент запуска: `multirun.py` 7b1f555d…,
  `cli.py` 30251354…, гейт db42672a…. После запуска слой дополнен
  (64000, якорь чекпойнта, путь заявки). Тест
  `TheRecordedGateReproducesTests` исполняет тот же гейт на
  закоммиченном слое и требует свидетельство, совпадающее с записанным
  целиком, вплоть до сообщений отказа. Это регрессия, а не второй гейт.

## Следствие правила «<= 165 на прогон» — факт, не решение

495 = 3 x 165 ровно, поэтому номинальные партии полны. Любое падение в
прогонах 1-3 выталкивает по заданию в следующий прогон, и всё упавшее
за три номинальных прогона сходится в восстановительный — у него одна
попытка. Сценарий B это и показал: два падения, и понадобился четвёртый
прогон. Восстановительный берёт до 165 заданий, так что падения
номинальных прогонов он вмещает с запасом; STOP наступает, только если
упадёт что-то в нём самом.

## Ограничения платформы

Документация GitHub (Actions limits): очередь 24 ч — только для
self-hosted раннеров; прогон — до 35 суток, ожидание включено; матрица —
256 заданий на прогон. Задания, ждущие `max-parallel` дольше суток, этим
проектом ни разу не наблюдались: самая долгая ступень шла 15.3 ч. Если
платформа их всё же отменит, механика увидит обычные падения — но
систематические, и восстановительный прогон их не закроет.
