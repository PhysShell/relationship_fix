# LOCAL-0 — `xiaotianxt/tg` и локальная база Telegram Desktop

Вы правы, что моя прежняя картина была слишком грубой. Исправляю её первой
строкой, потому что это фактическая ошибка, а не оттенок.

```
tdata        → settings и cache, НЕ источник истории
db_storage   → локальные SQLCipher-базы с шардами сообщений
```

Это разные вещи, и я склеил их в одно «локально читать нечего». `tg` читает
второе.

## 1. Что подтверждено по репозиторию

Прочитаны `LICENSE`, `Cargo.toml`, `README.md` (v2.2.1).

| | |
|---|---|
| лицензия | **MIT** (`Copyright (c) 2026 xiaotianxt`) |
| стек | Rust, `rusqlite` с `bundled-sqlcipher-vendored-openssl` |
| источник | «本机 Telegram 桌面版 `db_storage`，包括当前 WAL 中已提交数据» — локальная база плюс закоммиченный WAL |
| безопасность чтения | «SQLCipher 只读连接、`query_only`、每个数据库独立的一致性快照» — read-only, `query_only`, согласованный снимок на базу |
| платформы | **macOS arm64; Linux glibc 2.35+ x86_64/arm64** |
| прямо заявленные ограничения | «**不支持 Windows**、移动端或网页版数据；**不恢复本地数据库里已经不存在的消息**；不保证导出 Telegram 未缓存的媒体» |

Это не reverse engineering с шестнадцатеричным дампом в зубах: работающий донор с
названными модулями (`database_keys.rs` — key-файл, salt, HMAC первой страницы;
`db.rs`/`query.rs`; `scanner.rs`; `export.rs`).

## 2. Как он добывает ключи — и вот здесь всё меняется

macOS, дословно из README:

```
sudo DevToolsSecurity -enable
osascript -e 'quit app "Telegram"'
sudo codesign --force ...          ← пере-подпись клиента Telegram
затем перехват key material при ЛОГИНЕ
```

Linux: то же через `sudo apt install gdb` и `sudo tg keys --method login`.
Ключевой материал остаётся на диске в `~/.tg/key_material.bin`.

То есть путь требует: **root**, **отключения защитной функции macOS**,
**пере-подписи чужого подписанного приложения**, **подключения отладчика к
работающему мессенджеру** и **хранения извлечённых ключей БД в новом файле**.

## 3. Решающее возражение — не Windows

Представим onboarding участника исследования про отношения:

> «Запустите это с правами администратора. Программа отключит защитную функцию
> системы, пере-подпишет ваш Telegram, подключит к нему отладчик, извлечёт ключи
> шифрования вашей базы сообщений и сохранит их на диск.»

Мы убирали ручной экспорт потому, что он **обременителен** и **напоминает о
наблюдении**. Замена просит человека **ослабить защиту собственного мессенджера**.
Burden, измеренный в кликах, падает. Burden, измеренный в том, что мы просим у
человека, вырастает несопоставимо.

Плюс практическое: это почти наверняка сработает как срабатывание EDR/антивируса,
а пере-подпись подписанного приложения — отдельный разговор с условиями самого
Telegram.

**Это этический вердикт, а не инженерный, и от поддержки Windows он не зависит
вообще.** Даже идеальный Windows-backend оставил бы ту же просьбу.

## 4. Ответ на вопрос «почему нет Windows»

README не объясняет причину. По механизму видно: захват идёт **отладчиком**
(lldb после пере-подписи на macOS, GDB на Linux). Windows-бэкенд означал бы
Windows Debugging API — правдоподобно, но это отдельная реализация, а не
переключатель.

Вопрос при этом **снят по существу**: §3 закрывает путь независимо от ответа.

## 5. Регрессия полноты, которую легко не заметить

```
официальный экспорт  →  тянет историю С СЕРВЕРА
                        (прослежено по `messages.getHistory` в экспортёре)

локальная db_storage →  то, что клиент закэшировал
                        «不恢复本地数据库里已经不存在的消息»
```

Локальный путь **менее полон**, чем тот, который он должен был заменить. Для
лонгитюдного окна это семантическая регрессия, а не нейтральный обмен. Правила
вытеснения кэша неизвестны и, в отличие от экспортёра, нигде не документированы.

## 6. Plan B проверен по исходнику, а не по issue

У Telegram Desktop **нет** ключа командной строки для экспорта. Полная таблица
переключателей — `Telegram/SourceFiles/core/launcher.cpp:595-608`:

```
-debug · -testagent · -key · -autostart · -fixprevious · -cleanup
-noupdate · -tosettings · -startintray · -quit · -workdir · -- · -scale
```

Значит автоматизация официального экспорта возможна только через UI. Это
**существенно менее инвазивно**, чем §2: мы не пере-подписываем приложение и не
трогаем ключи, а нажимаем те же кнопки, что человек. Семантика при этом остаётся
уже квалифицированной — `TELEGRAM_DESKTOP_JSON`, месяц работы не выбрасывается.

Минусы честные: brittle к обновлениям UI, требует qualification по версиям и ОС,
и допустимость автоматизации нужно проверить по условиям **до** того, как она
станет продуктовым путём.

## 7. Обновлённая карта пяти путей

| путь | рутинный UX | новый semantics track | статус |
|---|---|---|---|
| ручной Desktop export | плохой | нет | работает, квалифицирован, **тяжёлый** |
| **UI-автоматизация экспорта** | ~1 клик | почти нет | **Plan A на сегодня** |
| локальная `db_storage` | zero-touch после setup | да | **REJECT для участников** (§3), **ORACLE для разработчика** |
| TDLib / API | zero-touch | да | **заблокирован** применимостью условий |
| `tdata` reverse engineering | — | ад | REJECT, и это был неправильный источник |

## 8. Где `tg` всё-таки ценен

Как **oracle разработчика на собственном аккаунте**. Он читает другой срез
реальности: локальную базу против серверной истории. Сравнение `tg` и
официального экспорта на одном чате **измеряет полноту экспорта** — ровно то,
о чём `coverage.completeness` сегодня UNAVAILABLE, и что мы закрыли одним
контрпримером про 10000 сообщений.

Это законное и полезное применение. Участникам путь не предлагается.

## 9. Что дальше

Plan A — UI-автоматизация штатного экспорта — не даёт нуля рутинных действий и
поэтому **не достигает `C_target` в том виде, в каком он заморожен**. Честные
варианты:

1. **Смягчить `C_target`**: «ноль рутинных действий» → «одно нажатие без
   переключения контекста», и признать это в интерпретации null, как того
   требует control-arm memo §5.1.
2. **Дождаться юридической оценки TDLib** — единственный путь, дающий настоящий
   ноль, и он упирается не в технику.
3. Оставить ручной экспорт и **принять тяжёлую контрольную руку** явно.

Выбор ваш, и он влияет на причинный контраст, а не только на UX.
