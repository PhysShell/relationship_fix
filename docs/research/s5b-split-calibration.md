# Калибровка экономии деления ключей: зачем и как

Единственный параметр, из-за которого ступень 64000 не планируется, —
`UNDIVIDED_SHARE`. Проверено запуском на настоящем реестре после 16000:

```
units_for(64000, ledger) -> SplitEconomyUnmeasured:
  полный юнит ставки 96 весит 7.81 ч против бюджета 2.5 ч,
  а экономия деления ключей НЕ ИЗМЕРЕНА (UNDIVIDED_SHARE is None)
```

## Связывающее число — 9.74 ч, а не 7.81 ч

7.81 ч есть ПЕРВЫЙ отказ: планировщик падает на первой же руке, не дойдя
до конца сетки. Худший полный юнит на 64000 весит **9.74 ч** (эффективная
ставка 120 = 96 × 1.25). Разница меняет все пороги:

```
                                  по 7.81 ч     по 9.74 ч
ускорение до потолка 5.83 ч          1.34x         1.670x
ускорение до цели 2.5 ч              3.124x        3.896x
идеальное деление на 2               3.91 ч        4.87 ч
идеальное деление на 4               1.95 ч        2.43 ч
порог s, при котором 4 групп хватает <= 9.35%     <= 0.89%
```

Порог для четырёх групп падает до 0.89% — ниже собственного замера науки
(`GENERATION_SHARE = 0.05`: 60 периодов дали 0.06 с на генерацию против
1.06 с на работу по 72 ключам). Значит четыре группы целевой бюджет не
берут даже в оптимистичном сценарии.

## Сколько групп нужно худшему юниту

```
     s   ->2.5 ч   ->5.83 ч    юнитов   CPU, ч   makespan@6 слотах
  0.00        4         2         253     405.3      67.6 ч
  0.05        5         2         266     449.5      74.9 ч
  0.0935      6         2         286     503.9      84.0 ч
  0.15        8         2         331     620.2     103.4 ч
  0.25   невозможно     3          —         —          —
```

При s = 0.25 цель недостижима ни при каком законном числе групп:
асимптота 2.44 ч формально ниже 2.5 ч, но потолок в 72 группы (по одному
ключу) оставляет 2.54 ч. Это чистый KILL для цели 2.5 ч.

39 из 156 рук превышают бюджет на 64000, 33 превышают потолок задания.
От неизмеренного параметра зависит четверть сетки, а не пара рук.

## Почему все варианты в ОДНОМ задании

Единственное прежнее касание оси деления — дымовая проба, гонявшая одну
группу из двух. Её факт был ближе к «половина ключей стоит как все», чем к
модельным 0.525, но развести это с классом раннера нельзя: менялись
одновременно ступень, доля ключей и раннер.

Наблюдённый разброс раннеров 1.96× БОЛЬШЕ разницы, которую ищем. Поэтому
варианты идут последовательно в одном задании: отношение времён тогда не
содержит межраннерной дисперсии вовсе, и одной руки достаточно.

## Почему ступень 4000, а не 16000

В модели `s` не зависит от просмотра: генерация идёт на период, работа по
ключам — на период на ключ. Полный свип одной самой тяжёлой руки
(1 группа + 2 группы + 4 группы) на 4000 стоит около 2 ч против 8 ч на
16000, то есть в задание на 16000 он не влезает вообще.

НЕЗАВИСИМОСТЬ `s` ОТ ПРОСМОТРА САМА НЕ ПРОВЕРЕНА. Peak RSS растёт втрое
от 4000 к 16000, так что эффекты памяти исключить нельзя. Подтверждение на
16000 — отдельное решение, и этим воркфлоу оно не запускается: ступень
жёстко ограничена 4000.

## Что измеряется

Для каждой группы: её ключи, время стены, время ЦП, высшая вода RSS, число
концов. Для варианта из g групп:

```
C_g = сумма времён всех групп     -> повторяемая неделимая работа
W_g = максимум по группам         -> straggler, именно он задаёт makespan
разброс = max / min по группам
```

Доля выводится алгеброй, а не подгонкой. Сумма по группам равна
`T1 * (1 + (g - 1) * s)`, отсюда

```
s_g = (C_g / C_1 - 1) / (g - 1)
```

то есть `s_2 = C_2/C_1 - 1` и `s_4 = (C_4/C_1 - 1)/3`. Для каждого g
печатается СВОЁ значение: если они расходятся, модель неверна, и
усреднять их в удобное число нельзя.

`s` и БАЛАНС мерятся раздельно. Прекрасное `s` ничего не гарантирует, если
одна группа систематически получает самые дорогие ключи: на 64000 нас
интересует `max(время группы)`, а не красота формулы. Разрез идёт смежными
срезами канонического порядка ключей, и при g = 4 это ровно по одной
первой координате ключа на группу (1.0 / 5.0 / 15.0 / 60.0) — если
стоимость от неё зависит, дисбаланс будет виден сразу.

## Пороги остановки

```
CORRECTNESS KILL   любое расхождение слитого делёного с неделёным:
                   missing, unexpected, различие значения, иное число концов
                   -> опыт останавливается немедленно, дальше не мерит
MODEL KILL         s_2 и s_4 существенно расходятся -> модель планировщика
                   неверна, усреднять нельзя
64000 KILL         s >= 0.2462 -> цель 2.5 ч недостижима даже при 72 группах
INCOMPLETE         времени задания не хватает на следующий вариант ->
                   записывается как INCOMPLETE, а не как измерение
```

Охранник времени считает по ХУДШЕМУ случаю: вариант из g групп может
стоить `g x T1` (это s = 1, деление не экономит ничего). Иначе таймаут
задания стал бы суррогатом измерения.

`GENERATION_SHARE = 0.05` в измеренное значение НЕ подставляется: это
замер одной составляющей (генерация против работы по ключам), а
`UNDIVIDED_SHARE` обязан описывать фактическую неделимую долю всего пути
исполнения.

## Что уже известно бесплатно

Механика прогнана локально на настоящей науке при игрушечном просмотре:
деление на 2 и на 4 группы дало ПОБИТОВО тот же результат, что неделёный
прогон — 216 концов, `missing 0`, `unexpected 0`, различий значений 0.
Ось, которая не включалась ни на 4000, ни на 16000, включилась и науку не
сломала. Это не замер экономии: времена там сотые доли секунды, шум
полностью перекрывает сигнал.

## Границы этого воркфлоу

Ступень только 4000. Одно задание, без матрицы. Реестр не трогается,
ступень лестницы не считается: на выходе исполнительный параметр.
`s5b-stage1.yml` не изменён, поэтому контракт «заявка это только сигнал»
у ступеней остался нетронутым. Пина заявки здесь нет намеренно:
закреплять нужно `SCIENCE_SHA`, от которого зависит сравнение делёного с
неделёным, и он закреплён отдельным checkout'ом.

Ступень 64000 не заказывается и после этой калибровки: измерение даёт
только вход для решения, а не разрешение.
