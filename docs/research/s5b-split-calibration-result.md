## 4. Amdahl: ЧЕТЫРЕ оценки, полоса 3.2–4.5%

Две из формул протокола и две бесплатные — из того, что половины вложены
в четверти (`half0 = q0 ∪ q1`, `half1 = q2 ∪ q3`), поэтому
`half − (q_i + q_j) = −T1·s` даёт `s` независимо от отношений `C_g/C_1`:

```
s_2 = C2/C1 - 1          = 0.0315
s_4 = (C4/C1 - 1)/3      = 0.0383
s_A = (q0+q1 - half0)/C1 = 0.0448
s_B = (q2+q3 - half1)/C1 = 0.0385
полоса 0.0315 .. 0.0448, размах 42% от нижней границы
```

Точечной оценки это не даёт: 42% размаха на четырёх оценках из ОДНОЙ
реализации — не тот результат, из которого делают константу с тремя
знаками. Но решение внутри полосы не меняется ни в одной точке: вся она
лежит выше порога для 4 групп (0.0089) и далеко ниже KILL-порога 0.2462.
**Ни `s`, ни его неопределённость 64000 не убивают.**

Для сведения: `GENERATION_SHARE = 0.05` (замер науки: 0.06 с генерации
против 1.06 с работы по 72 ключам) лежит чуть ВЫШЕ измеренной полосы.
Подстановка его вместо измерения дала бы консервативную ошибку, но это
совпадение порядка, а не подтверждение: величины определены по-разному.

## 5. Баланс: ГЛАВНАЯ НАХОДКА ПРОГОНА

Срезы смежные по каноническому порядку, и при g=4 четверти совпадают
ровно с первой координатой ключа. Стоимость по ней растёт монотонно:

```
координата   1.0:  490.1 с  ->  21.95 с/ключ
координата   5.0:  519.7 с  ->  23.59 с/ключ
координата  15.0:  600.3 с  ->  28.07 с/ключ
координата  60.0: 1156.6 с  ->  58.97 с/ключ
самый дорогой ключ дороже самого дешёвого в 2.69 раза
```

Модель «неделимая часть плюс работа по ключам» проверяется НЕ этими
числами: равенство суммы делимых частей и `C1·(1−s)` есть тождество.
Проверка — на варианте g=2, в подгонку не входившем: см.
`s5b-keycost-poc.md` (невязка 1.8% при объявленном допуске 5%).

**Внутри одной реализации структура согласована.** Порядок половин
совпадает с порядком четвертей (`half0 < half1` и `q0+q1 < q2+q3`),
четверти монотонны, а g=2 и g=4 — разные разбиения, измеренные разными
запусками внутри одного задания. Это говорит, что тяжесть здесь не шум
ОДНОГО замера. Устойчивость МЕЖДУ прогонами и раннерами не проверялась:
без неё статическая cost-aware раскладка рискует закрепить одну
реализацию.

Классификация: `C_g/C_1` НИЗКИЙ (1.032 и 1.115) при spread ВЫСОКОМ и
согласованном внутри прогона — это проблема РАСКЛАДКИ, а не повторяемой
работы.

## 6. Что это значит для 64000

Все числа ниже опираются на линейность по просмотру (×16 от 4000), а она
в модели помечена как допущение, а не замер
(`LOOK_LINEARITY_IS_ASSUMED_NOT_MEASURED`). Оценки условны.

```
скалярная модель при s = 0.0383            5–6 групп, худшая ~2.5 ч
СМЕЖНЫЕ срезы, как режет планировщик:
   g=4    худшая 5.14 ч   под потолком 5.83, выше цели 2.5
   g=5    худшая 3.57 ч   под потолком, выше цели
   g=8    худшая 2.78 ч   под потолком, выше цели
   g=11   худшая 2.26 ч   ВЛЕЗАЕТ в бюджет
cost-aware раскладка:
   g=6    худшая 2.19 ч   ВЛЕЗАЕТ в бюджет
```

Три следствия, каждое проверяемое:

**Скалярного `s` для планирования 64000 НЕ ХВАТАЕТ.** Модель обещает 5–6
групп, а смежная раскладка при том же `s` требует 11: разница целиком в
дисбалансе, который скаляр не описывает.

**Смежная раскладка требует 11 групп, cost-aware — около 6** (в масштабе
этого раннера ×16; в масштабе огибающей планировщика 8 и 5). Это не
косметика: каждая лишняя группа повторяет неделимую работу, то есть
раздувает суммарный CPU и число заданий.

**Калибровка не убила 64000 по экономии деления.** Существуют измеренные
параметры, при которых разбиение способно уложить группы в бюджет.
Производственная выполнимость 64000 при этом НЕ установлена: не
проверены линейность по просмотру и межпрогонная устойчивость стоимости
ключей, а нынешняя модель стоимости планировщика с измеренным дисбалансом
несовместима (см. `s5b-keycost-poc.md`).

Запас у 4 групп — 5.14 ч против потолка 5.83 ч, то есть 13%. Эти 5.14 ч
уже посчитаны на раннере, который был медленнее ВСЕХ шести ранее
наблюдённых при этой ставке; насколько далеко уходит хвост медленных
раннеров, неизвестно. Запас такого размера сопоставим с наблюдённым
разбросом раннеров и надёжным не считается.

## Чего этот прогон НЕ сделал

`UNDIVIDED_SHARE` в коде НЕ выставлен и остаётся `None`: измерение даёт
вход для решения, а не разрешение его подставить. Раскладка не изменена.
Ступень 16000 не запускалась, 64000 не заказывалась.

Открытыми остаются два вопроса, и оба важнее уточнения `s` третьим
знаком: линейность по просмотру (все оценки 64000 висят на ней) и
устойчивость постоянной стоимости ключа между прогонами, без которой
cost-aware раскладка рискует закрепить одну реализацию.
