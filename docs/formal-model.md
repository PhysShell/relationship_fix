# Формальная модель: что доказано, что проверено, что просто наблюдалось

**Зачем.** В документации проекта появились фразы вида «hard invariant»,
«sharp identified set», «valid outer envelope», «must hold under refinement».
Это математические теоремы, притворяющиеся комментариями. Через три недели
никто не вспомнит, почему `N` обязан вкладываться, а временная оболочка не
обязана — человеческая память для такого количества «это теорема / это только
диагностика / это внешняя оценка / это резкое множество» не предназначена.

**Главное правило этого файла.** Ни одно утверждение не называется
доказанным, пока не стоит в первой таблице. Написать «BOUNDED formally
verified», когда доказано ядро порядка, — ровно тот вид рекламы, ради
недопущения которого файл и заведён.

## Статусы

```
PROVED IN LEAN         машинно проверено, доверенная база напечатана
TESTED AGAINST ORACLE  проверено независимой исполнимой семантикой
EMPIRICAL ONLY         наблюдалось на данных; теоремой не является
ASSUMPTION             принято явно, не выведено
DEFERRED               не сделано, и известно, что не сделано
```

## 1. PROVED IN LEAN

Ядро: `formal/`, Lean 4.34.0, **без Mathlib** — только `List.Perm` из core.
Доверенная база каждой теоремы напечатана `#print axioms`.

**ДОВЕРЕННАЯ БАЗА ВЫРОСЛА, и это записано построчно, а не усреднено.** Первые
пять теорем обходятся **одним `propext`**. Корректность границ DP втянула
стандартную классическую тройку `[propext, Classical.choice, Quot.sound]` —
не из-за экзотики, а из обычных библиотечных лемм про `List` и из `omega`.
Это та же тройка, на которой стоит формализация Ферма; охотиться за
`Classical.choice` внутри ядра Lean было бы днями работы при нулевом
эпистемическом выигрыше. Но прежнее «у нас база меньше, чем у FLT» для новых
теорем больше не верно, и `FinalCheck` пинит **разные** наборы для старых и
новых строк.

`sorryAx` не встречается нигде. Проверяется скриптом `formal/scripts/audit.sh`, который
падает и на `sorry`, и на `axiom`, и на `native_decide`.

| теорема | утверждение |
|---|---|
| `coarsening_preserves_fine_orders` | `Admissible blocks.flatten l → Admissible (coarsen blocks) l` — огрубление только **стирает** ограничения порядка |
| `n_identified_set_monotone`, `n_identified_subset` | `I_N(fine) ⊑ I_N(coarse)` — идентифицированное множество `N` только расширяется |
| `bounded_collapses_on_total_order` | однородные корзины ⇒ допустимая история ровно одна |
| `n_identified_set_collapses` | там же множество одноточечное и равно обычному экстрактору |
| `identified_nonempty` | множество никогда не пусто |
| `admissible_flatten`, `admissible_perm`, `admissible_split`, `admissible_append` | структурные леммы допустимости |
| `perm_eq_of_uniform` | перестановка однородного списка равна ему |
| `coarse_key_factors` | `fine ∣ coarse → t / coarse = (t / fine) / (coarse / fine)` |
| `same_fine_key_same_coarse_key` | одинаковый мелкий ключ ⇒ одинаковый грубый |
| `block_balance` | чередование одним равенством: `pb + 1 = qb + [первый партнёр] + [последний партнёр]` |
| `mem_patterns` | перечисление содержит любую тройку, согласную с чередованием |
| `bucket_effect_complete` | **перечисление эффектов корзины ничего не теряет** |
| `history_to_reachable` | каждая реальная история присутствует среди достижимых пар DP |
| `dp_bounds_sound` | **`DPBoundsSound`: границы DP ограничивают КАЖДУЮ допустимую историю** |

Что здесь **существенно**: `N` зависит исключительно от допустимой топологии
порядка. Временной бюджет `min(Δ, c·H)` в эти утверждения не входит и сломать
их не может. Поэтому нарушение вложения по `N` есть баг в огрублении, сборке
корзин или DP — и никакое рассуждение про секунды его не оправдает.

## 3. EMPIRICAL ONLY

| наблюдение | где |
|---|---|
| вложение **внешней временной оболочки** `I_outer(1 с) ⊆ I_outer(60 с)` | держится на случайных трассах и проверяется на корпусе — **диагностика, не теорема** |
| оценка STRICT лежит **вне** идентифицированного множества | наблюдалось на реальных диадах; машинно проверяемый witness — DEFERRED |
| добавочная потеря STRICT, передаточная функция, разложение ширины, связь с плотностью | прогон по 520 диадам |

Почему вложение оболочки **не** теорема: `outer(1 с)` сама содержит значения,
физически недостижимые, а `outer(60 с)` обязана содержать **резкое**
множество при 60 с, а не все ложноположительные точки мелкой аппроксимации.

Формулировка, разделяющая математику и консервативность аппроксимации:

> Refinement monotonicity is a theorem for the sharp order layer and an
> empirical diagnostic, not a theorem, for the conservative temporal outer
> envelope.

Со сноской: «sharp order layer» здесь означает `N`. Слой порядка у `RMTR`
(`time_layer=False`) **между разрешениями не сравнивается вовсе** — там
латентность равна разности начал корзин, то есть величина сама зависит от
разрешения, и контрпример записан в `coarsening/verdict.py`.

## 4. ASSUMPTION

| допущение | почему принято явно |
|---|---|
| наблюдатель A: видны только метки, порядок внутри корзины неизвестен | наблюдатель B (доверяющий порядку строк) терял бы ноль; мы меряем цену собственного отказа, и это решение, а не факт |
| никакой вероятностной модели порядка внутри корзины | источник не сообщал, что `ABBA` столь же вероятно, как `AABB` |
| eligibility считается по **началу корзины** | та же метка, что видит обычный экстрактор; истинное время гуляет внутри корзины |
| правило вклада `min(Δ, c·H)` для закрытых внутри корзины возможностей | спаны не пересекаются, поэтому сумма ≤ Δ. Аргумент верный, но в Lean не формализован |

## 6. Слои проверки, и что каждый ловит

Три слоя, и они разные не для красоты:

```
grep по исходникам        ловит НАПИСАННЫЙ sorry
#print axioms + shell     ловит ТРАНЗИТИВНЫЙ sorryAx
#guard_msgs               ловит ЛЮБОЕ изменение доверенной базы
statement integrity       ловит подмену ВОПРОСА
```

Первый — policy check, а не proof check: `sorry` умеет приезжать импортом, и
grep по своим файлам этого не увидит. Второй это закрывает. Третий закрывает
то, чего не видят оба: если теорема завтра начнёт зависеть от
`Classical.choice` или от чьей-нибудь свежей `axiom miracle`, спрятанной за
пятью леммами, первые два скажут «всё прекрасно, sorryAx нет», а `FinalCheck`
покраснеет.

Запрещённые конструкции: `sorry`, `admit`, `axiom`, `unsafe`, `partial`,
`native_decide`, `implemented_by`, `extern`. Сканируется КОД, а не
комментарии — иначе собственные пояснения, объясняющие, почему `sorry`
нельзя, роняли бы сборку.

### Statement integrity: главное, чего не закрывал прежний audit

Главная угроза на нынешней стадии уже не `sorry` — его ноль. Угроза
противнее:

> доказать безупречно корректную теорему о **незаметно изменённой** модели.

```
не могу доказать  ->  слегка «улучшаю» определение  ->  доказываю  ->  QED
```

Поэтому вопрос и ответ разведены физически:

```
TrustedSpec/     определения И формулировки. Меняется редко, хэши в сертификате
Proofs/          доказательства. Меняются часто
Verification/    Challenge (вопрос, := sorry), Solution (ответ), судья, FinalCheck
```

`Challenge.lean` импортирует **только** `TrustedSpec`. Это не педантизм: если
бы он зависел от слоя доказательств, достаточно было бы «улучшить» общее
определение — и challenge с solution съехали бы вместе, дружно согласившись
друг с другом. Охрана, в которой вор сам обновляет фотографию разыскиваемого,
охраняет плохо. Обратный импорт тоже запрещён гейтом.

`StatementIntegrity.lean` проверяет:

1. тип challenge-теоремы **совпадает** с типом solution-теоремы;
2. этот тип есть в точности **замороженная константа** из `TrustedSpec`, а не
   её развёрнутая копия, которая могла бы разойтись;
3. solution не зависит от `sorryAx` и не выходит за allowlist `[propext]`;
4. challenge, наоборот, **обязан** зависеть от `sorryAx` — иначе это не дыра
   в задании, а чьё-то доказательство, пролезшее в вопрос.

### Оба гейта проверены диверсией

Гейт, который ни разу не падал, работоспособным не считается.

* В `Solution` подменена формулировка на соседнюю → сборка упала с
  `STATEMENT DRIFT: ... имеют РАЗНЫЕ типы`. Восстановлено.
* В `FinalCheck` изменена одна прибитая строка доверенной базы → `#guard_msgs`
  упал с точным диффом. Восстановлено.

### Замороженные открытые вопросы — и исправленная цель

Первая редакция замораживала не то. Было:

```
SoundSharpBoundsExist := ∃ lo hi, DPSound lo hi ∧ DPSharp lo hi
```

и это **не** soundness нашего DP. Здесь не фигурирует ни алгоритм, ни его
переходы, ни вычисляемые им границы. Утверждение выполняется тривиально —
возьмите сам минимум и максимум по допустимым историям, — и, доказав его,
можно получить зелёного судью, оставив production-DP полностью за кадром.
Сигнализация стояла не на той двери, ровно того класса, от которого судья и
строился.

Исправлено: лемма переименована в `SharpBoundsExistAbstract` и целью больше
не числится. В `TrustedSpec/ReferenceDP.lean` появилась **референсная
семантика DP** — сжатые шаблоны чередования, эффект корзины, свёртка по
состоянию, — и теперь целями заморожены две теоремы, **называющие эти
границы**:

```
DPBoundsSound  ∀ o l, Admissible o l → lo(dpBounds o) ≤ N l ≤ hi(dpBounds o)
DPBoundsSharp  ∀ o, обе границы ДОСТИГАЮТСЯ на какой-то целостной истории
```

Разделены намеренно: если резкость сломается, корректность останется ценной
сама по себе.

Область сужена: утверждения про `NTopological`, а **не** про production
`N_eligible` — см. следующий раздел.

Референсная семантика проверена перебором на 18 наблюдениях (совпадение с
полным перебором допустимых историй, 0 расхождений). Это **смоук-тест
определения**, а не доказательство: он лишь гарантирует, что мы не заморозили
теорему про заведомо неверный алгоритм.

`FinalCheck` пинит и обратное направление: все три открытых вопроса обязаны
зависеть от `sorryAx`. В день, когда перестанут, строки покраснеют — и это
будет место, где теорему надо переносить из Challenge в Solution.

### Область теоремы про `N`: уточнена контрпримером

Доказанная монотонность относится к `NTopological` — числу серий партнёра,
**без** календарного отсечения. Production `count_bounds` отсекает по
`start + H ≤ window_end`, а огрубление двигает `start` **назад**, поэтому
грубая рука может признать eligible то, что мелкая не признала:

```
одно партнёрское сообщение в t = 119, H = 60, окно до 120
   N(1 с)  = [0, 0]     119 + 60 = 179 > 120  — не eligible
   N(60 с) = [1, 1]     корзина с 60,  60 + 60 = 120 — eligible
   {0} НЕ вложено в {1}
```

Значит «вложение N — теорема» безусловно верно для `NTopological`, а для
`N_eligible` — только при **устойчивой eligibility**.

**Прогон Q1c этому условию удовлетворяет**, и это не везение: `bounded_q1c.py`
берёт `window = last + horizon`, поэтому любая корзина начинается не позже
последнего события и eligible все — на обеих шкалах. Там `N_eligible =
NTopological`, и результаты 517 диад не затрагиваются.

Показательно, почему этого не поймал property-тест: он брал то же
`window = stamps[-1] + horizon` и **никогда не заходил** в область, где
утверждение ложно. Тест, который не может упасть, ничего и не проверяет.
Теперь контрпример стоит отдельным regression-тестом.

Общая семантика eligibility на грубой границе — когда корзина **пересекает**
отсечку и сама eligibility становится частично идентифицированной — статус
**DEFERRED до S6**. Строить её сейчас только потому, что обнаружился край
света, незачем.

### Терминологическая мина, обезвреженная до первого `simp_all`

`DPBoundsSharp` утверждает достижимость **обоих концов**. Из этого **не**
следует, что достижимо каждое целое между ними. Поэтому везде пишется

```
N   sharp identified BOUNDS [lo, hi]
```

а не более сильное «identified set = `[lo, hi]`». Разница записана отдельным
замороженным утверждением `Spec.IdentifiedSetIsContiguous`, которое **не
является целью**: для нынешнего вывода «STRICT N ниже ЛЮБОЙ совместимой
величины» достаточно резкой нижней границы, и ещё один математический чулан
открывать незачем.

### План доказательства заморожен вместе с целью

Чтобы «мы пошли другим путём» было видно, а не подразумевалось:

```
BucketEffectComplete    эффект любой перестановки ЕСТЬ в перечислении
      ↓                 (нужно для SOUNDNESS)
HistoryToReachable      все реальные N присутствуют в dpReachable
      ↓
DPBoundsSound

BucketEffectRealizable  каждый перечисленный эффект материализуется
      ↓                 (нужно для SHARPNESS)
ReachableToHistory      каждая достижимая пара — целостная история
      ↓
DPBoundsSharp
```

Локальная точность корзины разделена на две половины намеренно: корректность
границ требует только первой. Доказав её, мы уже получаем работающий вывод,
даже если вторая застрянет.

**Что уже доказано из этого плана** (`Proofs/Scan.lean`, `Proofs/Reachable.lean`,
`Proofs/Blocks.lean`):

| лемма | что даёт |
|---|---|
| `opps_eq_countFrom` | `opps` зависит от предыдущего актёра только через бит «это был партнёр» |
| `countFrom_append`, `stateAfter_append` | счёт и состояние складываются по конкатенации — это склеивает корзины |
| `dpReachable_eq` | свёртка `foldl` равна структурной рекурсии `dpFrom`; вопрос не изменён, доказана лемма |
| `blocksOf_partner` | партнёрские блоки — это и есть возможности |
| `blocksOf_prev` | влияние предыдущего актёра ровно на один блок, записано без вычитания на `Nat` |
| `stateAfter_eq_last` | состояние после непустого списка определяется последним актёром |

**LEAN ПОСТАВЛЕН НА ПАУЗУ. Стоп-линия достигнута.**

```
BucketEffectComplete -> HistoryToReachable -> DPBoundsSound -> СТОП
```

Почему именно здесь, а не после sharpness. Практически важный вывод —

> STRICT систематически даёт значение, несовместимое со ВСЕМИ допустимыми
> хронологиями

— требует **корректной нижней границы**, а не достижимости самой `lo`:

```
STRICT_N < lo            измерено на 517 диадах
lo ≤ N  ∀ admissible     ДОКАЗАНО В LEAN
⟹ STRICT_N < N           для любой совместимой истории
```

`DPBoundsSharp` добавил бы «и эта граница достигается» — приятно, но вывод
сильнее не делает. Достижимость при этом проверена независимым переборным
оракулом на микротрассах. Итоговая граница доверия:

| утверждение | статус |
|---|---|
| корректность границ DP по `N` | **PROVED IN LEAN** |
| резкость границ | TESTED AGAINST ORACLE |
| полная непрерывность identified set | **NOT CLAIMED** |
| мост модель ↔ Python | TESTED |
| внешняя временная оболочка | ORACLE + ASSUMPTIONS, не доказана |

Остальное — `BucketEffectRealizable`, `ReachableToHistory`, `DPBoundsSharp`,
`IdentifiedSetIsContiguous`, soundness временной оболочки, корректность
дробной оптимизации, comparator, nanoda — остаётся **DEFERRED**, пока для
них не появится конкретная причина. Не всё, что можно превратить в теорему,
обязано ею стать.

**Что Lean успел окупить**, прежде чем его поставили на паузу:

* поймал, что формализован `NTopological`, а в голове он назывался
  production `N_eligible` — с воспроизводимым контрпримером;
* заставил заметить, что первая «DP soundness» вообще не называла DP;
* развёл sharp bounds и полное identified set;
* вскрыл протухший `.olean` в verification-гейте;
* локально подтвердил, что `patterns` соответствует реальному чередованию.

Добыча богатая. Доказывать свою любовь к формальным методам самому Lean
больше не требуется.

**Чередование доказано — одним равенством вместо четырёх веток.**

Классификация непустого двухакторного списка распадается на четыре клетки:

```
P,P -> pb = qb + 1      P,Q -> pb = qb
Q,P -> pb = qb          Q,Q -> qb = pb + 1
```

Вместо них доказано `block_balance`:

```
pb + 1 = qb + [первый партнёр] + [последний партнёр]
```

Сходится по всем четырём клеткам. Выигрыш не косметический: ветку
«оканчивается участником» иначе пришлось бы вытаскивать через отрицание,
арифметику `Nat` и факт «актёров всего два».

**И ключевая совместимость тоже:** `mem_patterns` — перечисление `patterns`
содержит ЛЮБУЮ тройку `(first, pb, qb)`, удовлетворяющую ограничению
чередования и границам по числу сообщений. Это был главный кандидат на
расхождение между алгоритмом и семантикой. Расхождения нет.

Плюс вырожденные корзины: `allPartner_scan`, `allParticipant_scan` — для
ветвей `p = 0` / `q = 0`, чтобы не тащить смешанную арифметику туда, где
одного актёра вообще нет.

**Сборка оказалась ровно бухгалтерией**, как и предполагалось: `blocksOf_pos`
и `blocksOf_le_countP` дали границы, `block_balance` — состояние,
`countFrom_carried` — счёт, `mem_patterns` — членство. Новой математики не
потребовалось, `TrustedSpec` не менялся. Аварийный выход не понадобился.

Судья: **8 claimed, 6 open**. Оба гейта снова проверены диверсией — подмена
типа у `dp_bounds_sound` уронила сборку с `STATEMENT DRIFT`; кроме того,
судья сам поймал мою забывчивость: `DPBoundsSound` остался в списке открытых
вопросов после того, как был доказан, и сборка отказалась это принять.

## 8. Threat model: чему научил протухший `.olean`

Гейт был зелёным и проверял вчерашний артефакт.

`Verification` намеренно не входит в дефолтный таргет — дерево доказательств
не должно импортировать `Challenge`. Из-за этого `lake build` не пересобирал
судью, а `lake env lean FinalCheck.lean` компилировался против **старых**
`.olean`. Обнаружилось случайно: я переименовал константы, и он вдруг
перестал их находить. До этого он честно зеленел на предыдущей редакции
вопроса.

Вывод в threat model, а не только в историю коммитов:

> «у нас аудит зелёный» успокаивает примерно так же, как зелёная лампочка на
> отключённой пожарной сигнализации.

Поэтому `audit.sh` теперь собирает `RelationshipFix.Verification` явно, а
`LEAN_PATH` сбрасывается — иначе теорему можно «доказать» случайным `.olean`
из соседней помойки. Практическое правило: гейт обязан проверять артефакт,
который он же только что собрал, и ни при каких обстоятельствах — найденный.

## 9. Чего здесь НЕТ: upstream comparator и второй kernel

`leanprover/comparator` делает то, чего локальный судья не делает: собирает
challenge и solution в **разных окружениях** и переигрывает доказательство
ядром заново. Он **не запущен**, и причины конкретные:

* требует Lean `v4.35.0-rc2`, проект запинен на `4.34.0`;
* требует `landrun` (Go, Landlock) и `lean4export`, совместимый с версией;
* запускается через `systemd-run --user`, а здесь сессии нет;
* его собственное допущение №6 — «вы не под привилегированным пользователем»
  — в этом контейнере нарушено: мы root.

Изображать его запуск было бы ровно тем оверклеймом, ради недопущения
которого заведён этот файл. Статус — **DEFERRED**, и то, что сделано вместо,
названо выше своим именем: локальная проверка целостности формулировки.

Второй независимый kernel (`nanoda`) — тоже DEFERRED, и сознательно. Он
закрывает риск «баг в ядре Lean». Текущий порядок рисков другой:

```
1. неверная формальная семантика
2. дрейф формулировки          <- закрывается судьёй
3. рассогласование модель ↔ Python  <- закрывается bridge-тестами
4. ошибка доказательства       <- закрывается ядром Lean
...
999. баг самого ядра Lean      <- закрывал бы nanoda
```

Второй kernel сейчас очень качественно охранял бы не тот вход.

## Как воспроизвести

```
cd formal && ./scripts/audit.sh
```

Скрипт сбрасывает `LEAN_PATH` — иначе теорему можно «доказать» случайным
`.olean` из соседней помойки и потом три часа искать привидений. Он же
печатает сертификат: коммит, версию Lean, тулчейн и **хэши TrustedSpec и
Challenge**, чтобы правку вопроса нельзя было провести молча.

`lake clean` на каждую локальную правку не делается — это превратило бы
изменение комментария в монашеское испытание. Чистая пересборка уместна на CI
и перед релизом.

Тулчейн ставится одним архивом с `releases.lean-lang.org`; Mathlib не нужен,
сети при сборке не нужно. Ядро намеренно маленькое: оно должно собираться из
одного тулчейна, чтобы слово «доказано» не зависело от нескольких гигабайт
чужого кода.

## Порядок работ дальше

Следующая теорема — **не** Dinkelbach и **не** RMTR, а soundness DP по слою
порядка: каждая выданная граница действительно ограничивает все допустимые
истории. После неё — sharpness, затем исполнимый перечислитель (он же даст
машинный witness про STRICT), и только потом временной слой и отношение.

Если очередная теорема начнёт требовать костылей, это диагноз семантики, а не
повод уговаривать prover.
